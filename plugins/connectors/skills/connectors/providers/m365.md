# Microsoft 365 — the facts behind `/connectors`

Every command, ID, portal label and error code here was checked against Microsoft's documentation
in **September 2026**; the source for each section is in **Sources** at the bottom. Microsoft
renames portal labels regularly — when one does not match, say what you are looking for and check
the linked page rather than guessing.

What the `m365` plugin does, so the steps below make sense:

- Consent: `https://login.microsoftonline.com/organizations/v2.0/adminconsent` with
  `scope=https://graph.microsoft.com/.default` — so the admin is asked for exactly the permissions
  **configured on the app registration**, and the app must be **multi-tenant**.
- Callback: `<APP_URL>/api/hooks/connectors/m365/callback` (the `connectors` plugin's public mount).
- Tokens: client credentials against the customer's tenant, with `M365_CLIENT_ID` /
  `M365_CLIENT_SECRET` (operator app) or the organisation's own id + secret (BYO, sealed in the
  database). No refresh tokens; a token lasts about an hour and is re-minted automatically.
- Reads: `users/delta`, `groups/delta` (with members), and `users/{id}/calendarView/delta` for
  members only, −30…+90 days, UTC. Tokens are only ever sent to `graph.microsoft.com`.

## The three permissions

All are Microsoft Graph **application** permissions (type `Role`), all require admin consent.
Microsoft Graph's app id is `00000003-0000-0000-c000-000000000000`.

| Permission | Application permission ID | Why the plugin needs it |
|---|---|---|
| `User.Read.All` | `df021288-bdef-4463-88db-98f22de89214` | people in the directory, to match them to members |
| `Group.Read.All` | `5b567255-7703-4780-807c-7be8301ae99b` | groups and their memberships |
| `Calendars.Read` | `798ee544-9d2d-430c-a058-570e29e34338` | the calendars of members who use this app |

Do not use the *delegated* IDs by mistake (they differ: e.g. delegated `User.Read.All` is
`a154be20-…`). An app registered in the portal also gets delegated `User.Read` by default; it is
harmless here and may be removed.

## Operator setup with the Azure CLI

**Prerequisites**

- A Microsoft Entra **work or school** tenant to own the app (a personal Microsoft account works
  for testing but can never be publisher-verified). The app is registered once and used by every
  customer organisation.
- An account there that can register applications: at least **Application Developer** (in tenants
  that leave "users can register applications" on, any member can).
- The Azure CLI (`az version` prints a JSON block when it is installed):
  - macOS: `brew update && brew install azure-cli`
  - Windows: `winget install --exact --id Microsoft.AzureCLI` (then open a new terminal)
  - Linux: follow the page for your distribution (Ubuntu/Debian `apt`, RHEL `dnf`, SLES `zypper`)
    at <https://learn.microsoft.com/en-us/cli/azure/install-azure-cli> — the apt route is several
    commands (Microsoft's signing key, then the repository, then `sudo apt-get install azure-cli`).
  - No subscription is needed: everything below is a directory (`az ad`) command.

**1. Sign in (human step — it opens a browser)**

```bash
az login --allow-no-subscriptions --tenant <tenant-id-or-primary-domain>
az account show --query "{tenant:tenantId, user:user.name}" -o table
```

`--allow-no-subscriptions` is what lets `az` sign in to a tenant that has no Azure subscription —
most Microsoft 365 tenants. Add `--use-device-code` on a machine with no browser.

**2. Decide the redirect URIs** — one per environment, exactly
`<APP_URL>/api/hooks/connectors/m365/callback`. `APP_URL` is in `apps/web/.dev.vars` (local,
normally `http://localhost:3000`), `apps/web/wrangler.staging.toml` and `apps/web/wrangler.toml`.
Rules that matter: `https` is required except for `localhost` (`http://localhost` is allowed, and
its port is ignored when matching); matching is case-sensitive; at most 256 characters each.

**3. Create the app, or find the one you made before**

Shell variables do not survive between separate commands you run, so every block below starts by
looking the app up by name.

```bash
APP_NAME="Rocketflare connectors"   # customer admins see this name on the consent screen
APP_ID=$(az ad app list --filter "displayName eq '$APP_NAME'" --query "[0].appId" -o tsv)
if [ -z "$APP_ID" ]; then
  APP_ID=$(az ad app create \
    --display-name "$APP_NAME" \
    --sign-in-audience AzureADMultipleOrgs \
    --web-redirect-uris \
      "http://localhost:3000/api/hooks/connectors/m365/callback" \
      "https://<staging-host>/api/hooks/connectors/m365/callback" \
      "https://<production-host>/api/hooks/connectors/m365/callback" \
    --query appId -o tsv)
fi
echo "App (client) ID: $APP_ID"   # not a secret
```

- `AzureADMultipleOrgs` = "Multiple Entra ID tenants" in the portal (older label: "Accounts in any
  organizational directory"). **Not** `AzureADandPersonalMicrosoftAccount`.
- Adding an environment later **replaces the whole list**, so pass every URI:
  `az ad app update --id "$APP_ID" --web-redirect-uris <all URIs>`; check with
  `az ad app show --id "$APP_ID" --query web.redirectUris`.

**4. Add the three application permissions**

```bash
APP_ID=$(az ad app list --filter "displayName eq 'Rocketflare connectors'" --query "[0].appId" -o tsv)
az ad app permission add --id "$APP_ID" \
  --api 00000003-0000-0000-c000-000000000000 \
  --api-permissions \
    df021288-bdef-4463-88db-98f22de89214=Role \
    5b567255-7703-4780-807c-7be8301ae99b=Role \
    798ee544-9d2d-430c-a058-570e29e34338=Role
az ad app permission list --id "$APP_ID" -o table
```

`az` then suggests running `az ad app permission grant`/`admin-consent` — **don't**, unless the
operator's own tenant is also an organisation being connected. Consent belongs to Mode 4.

**5. Create a client secret and store it without printing it**

`--append` is mandatory: without it `credential reset` **deletes every existing secret** on the app.
Use one secret per environment (the display name says which), so each can be rotated alone. Run
one reset at a time (a known CLI issue can lose an appended credential when two run back to back).

Local (`apps/web/.dev.vars`, run from the repository root):

```bash
APP_ID=$(az ad app list --filter "displayName eq 'Rocketflare connectors'" --query "[0].appId" -o tsv)
SECRET=$(az ad app credential reset --id "$APP_ID" --append \
  --display-name "local $(date +%F)" --years 1 --query password -o tsv)
[ -n "$SECRET" ] || { echo "no secret returned - stop"; exit 1; }
M365_CLIENT_ID="$APP_ID" M365_CLIENT_SECRET="$SECRET" node -e '
const fs = require("fs"), p = "apps/web/.dev.vars"
let s = fs.existsSync(p) ? fs.readFileSync(p, "utf8") : ""
for (const k of ["M365_CLIENT_ID", "M365_CLIENT_SECRET"]) {
  const line = `${k}=${process.env[k]}`, re = new RegExp(`^${k}=.*$`, "m")
  s = re.test(s) ? s.replace(re, () => line) : (s && !s.endsWith("\n") ? s + "\n" : s) + line + "\n"
}
fs.writeFileSync(p, s, { mode: 0o600 })
console.log("wrote M365_CLIENT_ID and M365_CLIENT_SECRET to " + p)'
unset SECRET
pnpm dev:stop && pnpm dev    # the Worker reads .dev.vars at start
```

Deployed (staging shown; for production drop `-c wrangler.staging.toml`). `wrangler secret put`
reads the value from stdin when it is piped, and **creates and deploys a new Worker version
immediately** — get a yes first:

```bash
APP_ID=$(az ad app list --filter "displayName eq 'Rocketflare connectors'" --query "[0].appId" -o tsv)
SECRET=$(az ad app credential reset --id "$APP_ID" --append \
  --display-name "staging $(date +%F)" --years 1 --query password -o tsv)
[ -n "$SECRET" ] || { echo "no secret returned - stop"; exit 1; }
printf '%s' "$APP_ID" | pnpm --filter @rocketflare/web exec wrangler secret put M365_CLIENT_ID -c wrangler.staging.toml
printf '%s' "$SECRET" | pnpm --filter @rocketflare/web exec wrangler secret put M365_CLIENT_SECRET -c wrangler.staging.toml
unset SECRET
pnpm --filter @rocketflare/web exec wrangler secret list -c wrangler.staging.toml   # names only
```

The kit's own path works too: put both keys in `apps/web/.provision.env` (git-ignored) or export
them, then the user runs `pnpm provision secrets <env>` — it sets every installed plugin's declared
secrets it finds there (and skips unset ones).

If the app was renamed, replace `'Rocketflare connectors'` in each lookup — or set `APP_ID` to the
client id directly.

**6. Diary the expiry, and rotate**

```bash
az ad app credential list --id "$APP_ID" --query "[].{name:displayName, expires:endDateTime, keyId:keyId}" -o table
```

The CLI default is **1 year** (`--years N` or `--end-date YYYY-MM-DD` to change it). The portal
caps secrets at **24 months** and Microsoft recommends **under 12**; a tenant's app-management
policy may enforce less. An expired secret shows up as `AADSTS7000222` and an `error` installation.
Rotate = step 5 again (new secret, `--append`), confirm the environment works (`pnpm cli
connectors sync`), then delete the old one:
`az ad app credential delete --id "$APP_ID" --key-id <old keyId>`.

Microsoft now recommends certificates rather than secrets for production apps. The `m365` plugin
supports **client secrets only** today; certificate credentials are a planned follow-up.

## Operator setup in the portal (no CLI)

1. <https://entra.microsoft.com>, as at least **Application Developer**. Several tenants? The
   **Settings** (gear) icon switches directory.
2. **Entra ID → App registrations → New registration.** Name it; **Supported account types:
   Multiple Entra ID tenants**; **Register**. Copy **Application (client) ID** from Overview.
3. **Authentication →** (Redirect URI configuration) **Add Redirect URI → Web**, enter each
   `<APP_URL>/api/hooks/connectors/m365/callback`, **Configure**.
4. **API permissions → Add a permission → Microsoft Graph → Application permissions**, tick
   `User.Read.All`, `Group.Read.All`, `Calendars.Read`, **Add permissions**. Do **not** press
   "Grant admin consent" (see step 4 of the CLI route for why).
5. **Certificates & secrets → Client secrets → New client secret**, a description and an expiry
   (≤ 24 months), **Add**. Copy the **Value** — not the "Secret ID" — now; it is never shown
   again.
6. The human puts the values in place themselves (you never see the secret): locally by editing
   `apps/web/.dev.vars` (`M365_CLIENT_ID=…`, `M365_CLIENT_SECRET=…`) then `pnpm dev:stop && pnpm
   dev`; deployed by running, in their own terminal,
   `read -rs S && printf '%s' "$S" | pnpm --filter @rocketflare/web exec wrangler secret put M365_CLIENT_SECRET [-c wrangler.staging.toml]; unset S`
   (and the same for `M365_CLIENT_ID`).

## Publisher verification (before offering this to other organisations)

A human task; coach it, don't attempt it. It puts a blue **verified** badge on the consent screen.
Since November 2020, where a tenant enables risk-based step-up consent, *users* cannot consent to
newer unverified multi-tenant apps — **admins still can**, and this plugin only ever uses admin
consent, so an unverified app works; it just looks less trustworthy. Requirements:

- A **Microsoft AI Cloud Partner Program** account (its partner global account, not a location
  ID) that has completed verification. Free; no licence.
- The app registered with a work or school account, in a tenant associated with that partner
  account, with a **publisher domain** set that is not `*.onmicrosoft.com`.
- The partner account's verification email domain matches the publisher domain or a DNS-verified
  custom domain in the tenant.
- The person doing it: Application Administrator or Cloud Application Administrator in Entra, and
  Partner Admin or Account Admin in Partner Center, signed in with MFA.
- Then: App registrations → the app → **Branding & properties** (check the publisher domain is
  set) → **Add Partner ID to verify publisher** → the Partner One ID → **Verify and save**; the blue
  badge appears beside the publisher name. Full steps:
  <https://learn.microsoft.com/en-us/entra/identity-platform/mark-app-as-publisher-verified>.

## Bring your own app (for the customer's admin)

For an organisation that will not consent to the operator's app. Their admin does the portal steps
above **in their own tenant** — multi-tenant (consent goes through `/organizations`; a single-tenant
app fails with `AADSTS50194`/`AADSTS650059`), the same redirect URI (the operator tells them the
exact `<APP_URL>`), the same three application permissions, a client secret — and then, in this
app, Settings → Connections → tick **Use our organisation's own registered app** → client id +
secret → **Connect Microsoft 365** → consent as below. The secret is sealed with the deployment's
`OAUTH_ENCRYPTION_KEY` (missing → 503 `encryption_key_missing`) and never returned; expiry and
rotation are theirs — they re-enter a new secret the same way.

## Connecting (the customer admin)

- **Who can consent**: Global Administrator, or **Privileged Role Administrator**. Cloud
  Application Administrator and Application Administrator can consent to most things **except
  Microsoft Graph application permissions** — which is all this app asks for. In this app they need
  the owner or admin role.
- **What they see**: Microsoft's consent screen listing "Read all users' full profiles", "Read all
  groups" and "Read calendars in all mailboxes", the app's name and publisher (verified or not).
  **Accept** returns them to Settings → Connections.
- **Why calendars may be missing for someone**: calendars exist only for users with an **Exchange
  Online** mailbox (a licence that includes Exchange); on-premises or unlicensed mailboxes fail with
  `MailboxNotEnabledForRESTAPI` on that one person's cursor.
- **Undo on Microsoft's side**: Entra admin center → **Entra ID → Enterprise apps → All
  applications** → the app → **Properties → Delete** (Cloud Application Administrator or above;
  restorable for 30 days). Disconnecting in this app does not do this for them.

## Scoping calendar access to some mailboxes (advanced, customer-side)

`Calendars.Read` as an application permission covers every mailbox in the tenant. The plugin only
reads members' calendars, but an organisation that wants Microsoft to *enforce* a smaller set uses
**RBAC for Applications** in Exchange Online (it replaces Application Access Policies): an Exchange
admin creates a service-principal pointer (`New-ServicePrincipal`), a scope (`New-ManagementScope`
or an administrative unit), and assigns the role **`Application Calendars.Read`** with
`New-ManagementRoleAssignment … -CustomResourceScope …`; `Test-ServicePrincipalAuthorization`
checks it. Two traps: permissions are a **union** — the tenant-wide `Calendars.Read` consented in
Entra must then be **removed**, or the scope does nothing; and this plugin's **Re-grant consent**
button would add it back. Changes take 30 minutes to 2 hours to apply. Mailboxes outside the scope
then fail on their own cursor while the rest sync. This combination is not exercised by the
plugin's tests — treat it as a customer-run configuration and verify with `Test-ServicePrincipalAuthorization`.

## A tenant to test with

- **Microsoft 365 Developer Program sandbox** — a Microsoft 365 E5 tenant with 25 licences and
  sample users, mail and calendar data. It is **no longer open to everyone**: you qualify through a
  Visual Studio Professional/Enterprise subscription, an eligible Microsoft AI Cloud Partner
  Program tier or the ISV Success Program, or a Premier/Unified Support contract. Setup requires
  linking a billing account (it stays free). Sandboxes are short-lived (renewed with development
  activity; may be recreated every 90 days). <https://aka.ms/DevProgramDashboard>
- **Otherwise: a Microsoft 365 business plan trial** — one month free for up to 25 users, a credit
  card required, converting to paid unless recurring billing is turned off. Business Basic or
  Standard includes Exchange Online, so calendars work. Check the current terms before signing up:
  <https://learn.microsoft.com/en-us/microsoft-365/commerce/try-or-buy-microsoft-365>.
- A plain Entra tenant with no Microsoft 365 licences can test the **directory** sync only;
  calendars need Exchange Online mailboxes.

To see calendars in this app, a test user must also be a **member of this app** with the same
email as their Microsoft 365 `mail` (or UPN) — invite them from Settings → People.

## Troubleshooting

### Callback codes (red toast; `connectError=` in the Settings URL)

| Code | Meaning | Fix |
|---|---|---|
| `invalid_state` | The consent link expired (30 minutes), was tampered with, or came from another deployment | Press Connect again and finish within 30 minutes |
| `consent_not_granted` | The admin pressed Cancel (`access_denied`, AADSTS65004), or Microsoft did not report consent | Try again and Accept |
| `admin_consent_required` | Microsoft returned an error other than a cancel — usually the person is not a Global/Privileged Role Administrator | Have a Global Administrator or Privileged Role Administrator do it |
| `external_tenant_mismatch` | This organisation is already connected to a **different** Microsoft 365 tenant | Disconnect first, then connect the other tenant |
| `feature_disabled` | The `connectors` flag is off for this organisation | A global admin turns it on (Admin → Feature flags) |
| `installation_missing` | The pending installation was deleted while consent was in progress | Press Connect again |
| `provider_unknown` | The `m365` plugin is not installed on this deployment | Install it (`/rf-plugin`) |
| `consent_failed` | Consent succeeded but saving it failed — check the Worker log for `connectors: completing the installation failed` | Fix what the log says, press Connect again |

### Errors when pressing Connect (API envelope)

| Status / code | Meaning | Fix |
|---|---|---|
| 503 `connector_not_configured` | No operator app: `M365_CLIENT_ID`/`M365_CLIENT_SECRET` unset for this environment, or the dev server was not restarted after setting them | Mode 2, step 5 — or use BYO |
| 503 `encryption_key_missing` | `OAUTH_ENCRYPTION_KEY` is not set | Set it (`pnpm provision secrets <env>` generates it deployed; `.dev.vars` locally) |
| 404 `feature_disabled` | The flag is off | As above |
| 409 `installation_pending` (Sync now) | Consent was never completed | Press Connect / Retry consent |

### Installation and cursor errors (`pnpm cli connectors status`, the Connections card)

| Message starts with | Meaning | Fix |
|---|---|---|
| `Microsoft Entra refused the app: AADSTS…` (installation `error`) | The token request was refused — see the AADSTS table | Fix, then **Sync now** |
| `Microsoft Graph refused the directory read (401/403 …). Re-grant admin consent.` | A permission is missing or consent was revoked | **Re-grant consent**; check the three permissions are on the app |
| `Microsoft Graph request failed (403 …)` on one `calendar` cursor | That mailbox is excluded (Exchange scope) or not permitted | Expected if the customer scoped access; otherwise re-grant consent |
| `Microsoft Graph request failed (404 … MailboxNotEnabledForRESTAPI …)` | No Exchange Online mailbox (unlicensed, or on-premises) | Licence the user, or ignore — it affects only them |
| `Microsoft Graph throttled the request` | 429/503/504; the job waits for `Retry-After` and is not a failure | Nothing — see limits below |
| `Microsoft Graph discarded the delta token` | Microsoft expired the sync state; a full resync starts by itself | Nothing |

### AADSTS codes

| Code | Meaning (Microsoft's name) | Who fixes | Fix |
|---|---|---|---|
| AADSTS50011 | InvalidReplyTo — redirect URI not registered | Operator (or BYO admin) | Add exactly `<APP_URL>/api/hooks/connectors/m365/callback`; check `APP_URL` for the environment, scheme, host and case |
| AADSTS65004 | UserDeclinedConsent | Customer admin | Accept on the consent screen |
| AADSTS90094 | AdminConsentRequired | Customer admin | Sign in as Global Administrator or Privileged Role Administrator |
| AADSTS65001 | DelegationDoesNotExist — no consent in that tenant | Customer admin | Re-grant consent |
| AADSTS700016 | App not found in the directory/tenant | Customer admin or operator | Consent was removed (enterprise app deleted) → re-grant; or the client id is wrong (BYO typo, or a single-tenant app) |
| AADSTS7000229 | Client app is missing a service principal in the tenant (from Microsoft Q&A; not in the official table) | Customer admin | Consent never completed or the enterprise app was deleted → re-grant consent |
| AADSTS7000215 | Invalid client secret | Operator (or BYO admin) | Often the **Secret ID** pasted instead of the **Value**, or the secret was deleted by a `credential reset` without `--append` → new secret (Mode 2, step 5) |
| AADSTS7000222 | Client secret expired | Operator (or BYO admin) | Rotate (Mode 2, step 6) |
| AADSTS7000112 | Application is disabled | Customer admin | Re-enable the enterprise app in Entra |
| AADSTS90002 | Tenant not found | — | The tenant was deleted, or it is in a national cloud (not supported) |
| AADSTS500011 | Resource service principal not found in the tenant | Customer admin | Re-grant consent; if it persists, capture the full message |
| AADSTS50194 / AADSTS650059 | App is not multi-tenant (`AzureADMyOrg`) | Operator (or BYO admin) | `az ad app update --id <appId> --sign-in-audience AzureADMultipleOrgs`, or set Supported account types to Multiple Entra ID tenants |
| AADSTS90099 | App not authorised in the tenant for a partner (GDAP) delegated admin | Customer admin | Sign in with an account that belongs to the customer tenant itself |
| AADSTS50020 / AADSTS500208 | The signed-in account is not from that tenant / a personal account | Customer admin | Sign in with a work account of the tenant being connected |
| AADSTS53003 | Blocked by Conditional Access | Customer admin | Their Conditional Access policy blocks the sign-in; their admin adjusts it |

Anything else: <https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes>
(or `https://login.microsoftonline.com/error?code=<number>`), and report it.

### Throttling limits (for context)

Outlook (calendar) calls are limited **per app per mailbox**: 10,000 requests per 10 minutes and
**4 concurrent requests**; exceeding one mailbox does not affect others. Microsoft Graph overall:
130,000 requests per 10 seconds per app. The plugin sends `x-ms-throttle-priority: low` and honours
`Retry-After`.
